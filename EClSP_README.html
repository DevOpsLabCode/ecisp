Discovery Engine

A Python, provider-pluggable discovery and security-analysis engine. It authenticates to an in-scope cloud or Kubernetes environment, gathers configuration data, normalizes it, evaluates JSON-defined finding rules and display filters, applies approved exceptions, and produces a report. Web UI

ui/backend is a FastAPI service that imports the engine's run() function directly in-process — it does not shell out to the CLI. ui/frontend is a React + Vite dashboard. Scans run one at a time per feature area on a background worker thread (the engine's logger and asyncio event loop are process-global), fanning out internally via a thread pool for multi-repo scans.

Cloud Provider Scanning

Configure a provider, authenticate, launch a scan, browse findings. Two ways to cover many accounts: GCP and Azure support a native "whole organization" toggle in the engine itself; everything else uses bulk import — a CSV/XLSX/JSON file where each row is one account's full scan configuration, rows can mix providers, and invalid rows are skipped individually rather than failing the whole import.

Code Scanning: SAST + SCA + Secrets + IaC + DAST

The newest feature: scans a single codebase instead of a whole org, through the same scanner set plus Trivy (dependency vulnerabilities + hardcoded secrets) and an optional OWASP ZAP dynamic scan.

Upload an archive.zip/.tar/.tar.gz/.tgz, extracted under zip-slip/symlink/hardlink containment checks with per-file and total size caps, content read only — never executed. SpotBugs and Security Code Scan are skipped for uploads specifically, since both require compiling untrusted code.
Or a GitHub repo URLPublic repos need no auth. Private repos use GitHub's real OAuth Authorization Code flow in a browser tab — consent happens on github.com, the token is exchanged server-side and held in an httponly session cookie, never in a URL or readable by frontend JS.
SCA + SecretsTrivy runs against every scan (upload or repo), covering dependency CVEs and hardcoded secrets in one pass.
DAST, optionalOnce the source scan completes, supply an authorized running app URL to run ZAP's automation framework (spider → passive → active → passive → SARIF). Findings merge into the same result and report — not a separate output.
Repo-URL mode — a genuine branch lookup against a real public repository.
Scan detail — severity tiles, reports, DAST completion, and an expanded finding, all from a real completed run.

This exact flow was live-verified end to end: real zip-slip/symlink attack payloads rejected, a real GitHub OAuth consent screen → token exchange → session cookie, a real Trivy run detecting a genuine CVE and secret, a real ZAP run finding genuine issues (missing CSP, clickjacking protection, server version disclosure) merged into the same scan, and all five report formats downloading real content. CI/CD Pipeline

Three GitHub Actions workflows, scoped to ui/** so they don't run on engine-only changes.

ui-ci.yml

Backend tests+coverage+lint+SAST, frontend tests+coverage+lint+typecheck+build, Trivy dependency/secret scanning with SARIF upload, Lighthouse CI performance budgets, and a k6 latency smoke test against the always-available metadata endpoints. A final ci-summary job fans in every other job so branch protection needs only one required check.

ui-codeql.yml

CodeQL static analysis for both javascript-typescript and python, on push/PR plus a weekly schedule.

ui-deploy.yml

Builds both Docker images, brings the real stack online with docker compose, and smoke-tests it before publishing: health checks, a real scan job through a bogus AWS profile (asserting the engine itself ran and failed on its own auth check — this is what caught a real asyncio-event-loop bug during development), a real code-scan upload through the pipeline, and the k6 latency test against the live containers. Only publishes to GHCR if every check passes; pull-request runs build and test but never publish.

Setup & Deployment

Local development needs Python 3.9–3.11 for the engine and Node ≥22.22.2 for the frontend. The real way to run the full stack — including the eight-tool SAST toolchain, Trivy, and OWASP ZAP, none of which the plain uvicorn dev server has installed — is Docker:

cd ui
docker compose up --build
# backend:  http://localhost:8000
# frontend: http://localhost:8080

The backend Dockerfile builds from the repo root in multiple stages: one per toolchain (Python, Go, JVM+Maven, Ruby, .NET SDK, Node+ESLint, Trivy, OWASP ZAP), so a change to one toolchain's version doesn't invalidate every other stage's build cache. The private-repo "Connect GitHub" button needs a registered GitHub OAuth App, with its Client ID/Secret set via a gitignored ui/.env file — without it, the button reports "not configured" and every other feature still works.

Operational Notes

Report directories aren't prunedui/backend/data/{reports, orgscan-reports, codescan-reports} are evidence storage — manage retention yourself.
One scan at a time, per feature areaBy design — the engine's process-global logger/event-loop state makes concurrent runs on one worker unsafe. Org scans and code scans still fan out per-repo internally.
No auth on the backend APIBinds to localhost only in dev. Don't expose it beyond localhost without adding authentication — scan credentials and results are sensitive.
GitHub OAuth sessions are in-memoryRestarting the backend logs everyone's "Connect GitHub" session out — a deliberate scope choice matching how every other job manager here holds state.
